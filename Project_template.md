# Отчёт по проектной работе 7 спринта

RAG-бот для QuantumForge Software.

## 1. Исследование моделей и инфраструктуры

### 1.1. Контекст, требования и допущения

#### Контекст компании

QuantumForge Software — финско-эстонская продуктовая компания. Основной продукт — SaaS-платформа цифровых двойников промышленных объектов. Консалтинговое направление помогает клиентам интегрировать платформу с существующими SCADA-системами.

Документация распределена между репозиториями, Confluence, Google Drive и другими системами. Производственная инфраструктура использует AWS, включая EKS и RDS. Наличие этой инфраструктуры учитывается при сравнении вариантов размещения бота, но само по себе не определяет выбор решения.

| Характеристика базы знаний | Значение |
|---|---|
| Markdown/MDX-файлы в репозиториях | Около 18 000 |
| Страницы Confluence | Около 3 000 в 30 пространствах |
| PDF-спецификации | Около 250 |
| Прирост документации | Около 400 страниц в месяц |

Количество файлов и страниц не определяет размер векторного индекса: он также зависит от длины документов, размера и перекрытия чанков, размерности векторов и способа индексирования.

#### Заказчик и пользователи

Рабочее допущение: бизнес-заказчиком выступает руководство компании, заинтересованное в снижении трудозатрат на поиск информации и повышении продуктивности сотрудников. Конкретная должность заказчика и владелец эксплуатации системы не определены.

| Пользователи | Основные задачи |
|---|---|
| Разработчики | Поиск архитектурных решений, API-документации и описаний микросервисов |
| Сотрудники поддержки | Поиск способов решения типовых проблем пользователей |
| Менеджеры и аналитики | Поиск регламентов и бизнес-правил |
| Новые сотрудники | Получение инструкций для адаптации и начала работы |

GRC-команда является дополнительной заинтересованной стороной: подготовка к ежегодному SOC 2 review занимает около 140 часов из-за ручной сверки актуальных политик.

#### Проблемы и бизнес-цели

- Документы дублируются и расходятся по версиям; отсутствует единый порядок поддержания их актуальности.
- Новые инженеры тратят до четырёх часов в неделю на поиск информации; одинаковые вопросы регулярно поступают коллегам.
- Документация устаревает через 2–3 месяца после очередного крупного релиза.
- Подготовка к аудиту требует значительного объёма ручной работы.

Цели системы — сокращение времени поиска и повторяющихся обращений, ускорение адаптации сотрудников, выявление пробелов в документации и возможность расширения решения на другие команды. Процент экономии и целевые сроки достижения этих результатов не заданы.

RAG упрощает доступ к знаниям, но не устраняет противоречия и устаревание документов автоматически. Для эксплуатации необходимы владельцы контента, правила актуализации и обработка конфликтующих версий.

#### Границы учебного прототипа

Архитектурное исследование рассматривает масштаб и ограничения компании. Объём реализации ограничен прототипом со следующими требованиями:

- База знаний из минимум 30 документов открытой предметной области с заменой узнаваемых терминов и сохранением словаря замен.
- Построение, сохранение и загрузка векторного индекса с текстами фрагментов и метаданными источников.
- Поиск по вопросу пользователя и генерация ответа на основе найденных фрагментов.
- Few-shot примеры, краткое обоснование ответа по источникам и корректная обработка недостаточности данных.
- Проверка prompt injection при отключённой и включённой защите.
- Локальный запуск, запуск в Docker и сохранённые результаты контрольных обращений.

Интеграции с корпоративными источниками, синхронизация прав доступа, персонализация по ролям и автоматическая аналитика пробелов относятся к развитию производственного решения. В объём текущего прототипа их полноценная реализация не включена.

#### Критерии качества и ограничения

| Область | Критерий оценки |
|---|---|
| Поиск | Соответствие найденных фрагментов вопросу пользователя |
| Ответы | Подтверждение фактов источниками; корректное сообщение о недостатке информации |
| Производительность | Время построения индекса, задержка поиска и полное время ответа |
| Стоимость | Расходы на вычисления, хранение, обращения к внешним сервисам и сопровождение |
| Конфиденциальность | Контроль передачи документов, фрагментов и вопросов во внешние сервисы |
| Безопасность | Разделение инструкций приложения и недоверенного содержимого документов |
| Сопровождение | Воспроизводимый запуск, обновление индекса и возможность диагностики ошибок |
| Масштабирование | Влияние роста базы и количества одновременных запросов на ресурсы и задержки |

Для корпоративного решения принято проектное требование: поиск и формирование ответа должны учитывать права пользователя на документы. Фильтрация вредоносных инструкций не заменяет разграничение доступа.

#### Неопределённости и рабочие допущения

| Неизвестный параметр | Влияние на архитектурное решение |
|---|---|
| Количество пользователей, запросов и пиковая одновременная нагрузка | Конфигурация сервера, пропускная способность и стоимость эксплуатации |
| Средняя длина документов, языки и структура содержимого | Выбор embedding-модели, разбиение на чанки и объём индекса |

| Бюджет и доступные ресурсы сопровождения | Сравнение полной стоимости локального и облачного вариантов |
| Требуемая частота обновления базы и права доступа к источникам | Способ синхронизации, обновления индекса и фильтрации документов |

При отсутствии числовых требований расчёты стоимости и ресурсов могут быть выполнены только для явно обозначенных сценариев нагрузки. Такие оценки не являются измерениями производственной системы.

Рабочее допущение для учебного прототипа: база содержит открытые тексты с заменёнными терминами и не включает реальные корпоративные секреты. Для производственной системы допустимость передачи данных во внешние сервисы требует отдельного решения владельца данных; разрешение на такую передачу не предполагается по умолчанию.

### 1.2. Сравнение LLM

#### Объекты и метод сравнения

Для генерации ответов рассмотрены три конкретные модели: Qwen3-8B при самостоятельном размещении, GPT-4.1 mini через API OpenAI и YandexGPT Pro 5.1 через API Yandex Cloud. Сравнение охватывает качество ответов, скорость, стоимость и сложность эксплуатации. Итоговый выбор всего стека на этом этапе не выполнен.

Исследование основано на официальных характеристиках и тарифах, проверенных в сентябре 2026 года. Практические испытания на базе проекта ещё не проводились. Выводы о пригодности являются архитектурной оценкой; числовые показатели качества и задержки не заявляются.

Контекстное окно задаёт предел объёма обрабатываемого текста. Большое окно не гарантирует точности ответа и не заменяет отбор релевантных фрагментов.

Влияние оборудования и длины запроса рассматривается как фактор архитектурной оценки, а не как измеренный результат.

Сопоставление качества требует одинаковых вопросов и найденных фрагментов, проверки подтверждения ответа источниками, корректности отказа при нехватке данных и реакции на вредоносный контекст. Для скорости значимы время первого фрагмента ответа и полное время ответа при одинаковых ограничениях длины и сопоставимой нагрузке. Данных для ранжирования кандидатов по этим метрикам пока нет.

#### Стоимость использования

Тарифы приведены для обычных синхронных текстовых запросов без кеширования, пакетных скидок и встроенных платных инструментов. Единица сравнения — 1 млн входящих или исходящих токенов.

| Вариант | Входящие токены | Исходящие токены | Дополнительные затраты |
|---|---|---|---|
| Qwen3-8B на собственных ресурсах | Нет тарифа внешнего API за токен | Нет тарифа внешнего API за токен | Аренда или амортизация оборудования, электроэнергия, хранение, эксплуатация |
| GPT-4.1 mini | 0,40 USD за 1 млн | 1,60 USD за 1 млн | Работа приложения, поиск, хранение, сопровождение; возможные налоги |
| YandexGPT Pro 5.1, рублёвый тариф | 800 ₽ за 1 млн, с НДС | 800 ₽ за 1 млн, с НДС | Работа приложения, поиск, хранение и сопровождение |
| YandexGPT Pro 5.1, долларовый тариф | 6,557376 USD за 1 млн, без НДС | 6,557376 USD за 1 млн, без НДС | Те же статьи; применимость валютного тарифа зависит от платёжного аккаунта |

Источники тарифов: [GPT-4.1 mini](https://developers.openai.com/api/docs/models/gpt-4.1-mini), [Yandex: синхронная генерация](https://aistudio.yandex.ru/ru/docs/ai-studio/pricing#synchronous). Долларовая цена Yandex приведена из отдельного тарифа провайдера, а не получена пересчётом рублей. Цены из старых анонсов не используются для расчёта.

Расчётный пример, не измерение: 1 000 запросов, каждый содержит 2 000 входящих токенов и 300 исходящих. Вход включает инструкции приложения, примеры, найденный контекст и вопрос. Объём составляет 2 млн входящих и 0,3 млн исходящих токенов.

- GPT-4.1 mini: `2 × 0,40 + 0,3 × 1,60 = 1,28 USD`.
- YandexGPT Pro 5.1: `2 × 800 + 0,3 × 800 = 1 840 ₽` с НДС; по отдельному долларовому тарифу — около `15,08 USD` без НДС.

Сценарий использует условно одинаковые бюджеты токенов: один и тот же текст может давать разное количество токенов у разных моделей. Повторные запросы, ошибки, embeddings и инфраструктура в пример не включены. Поэтому эти суммы не являются бюджетом всей системы или результатом эксплуатационного сравнения.

Для локальной модели отсутствие тарифа за токены не означает нулевую стоимость. При редких запросах ресурсы могут простаивать; при постоянной нагрузке собственное размещение может стать экономически обоснованным. Точка окупаемости зависит от оборудования, достигнутой производительности и трудозатрат сопровождения и пока не рассчитана.

В карточке Qwen перечислены варианты локального исполнения, включая MLX-LM и llama.cpp. Конкретный движок и требования к памяти пока не выбраны. Размер весов не равен полной памяти процесса: дополнительно нужны память для контекста и рабочие буферы. [Источник](https://huggingface.co/Qwen/Qwen3-8B).

Для OpenAI API данные по умолчанию не используются для обучения моделей, если клиент явно не разрешил такое использование. При этом журналы контроля злоупотреблений могут содержать запросы и ответы и обычно хранятся до 30 дней; предусмотрены исключения. Режимы сокращённого хранения требуют отдельных условий и одобрения. [Политика обработки данных](https://developers.openai.com/api/docs/guides/your-data).

У Yandex заголовок `x-data-logging-enabled: false` отключает использование содержимого запросов для улучшения сервиса. Он не отключает все категории хранения: служебные логи, аудит, трейсы и данные, необходимые API, регулируются отдельно. [Отключение логирования](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/disable-logging), [политика хранения](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/security/data-storage).

Для размещения компании в Финляндии и Эстонии OpenAI API является доступным по списку поддерживаемых стран; это не подтверждает доступ конкретного аккаунта. Россия в перечне отсутствует, поэтому доступность API для учебного запуска рассматривается отдельно от архитектуры компании. [Поддерживаемые страны](https://developers.openai.com/api/docs/supported-countries).

#### Промежуточный вывод

При запрете передачи контекста внешним провайдерам приоритет получает размещение модели в разрешённом контуре. При допустимости внешней обработки облачные варианты снижают объём работ по эксплуатации самой LLM, сохраняя зависимость от сети, квот и тарифов.

Локальная LLM сама по себе не обеспечивает локальную обработку всей базы: облачная embedding-модель также получает исходные тексты. Итоговое решение по конфиденциальности зависит от всей цепочки обработки данных.

На данном этапе выделены три кандидата и условия их применимости. Окончательная конфигурация требует сравнения embedding-моделей, векторных хранилищ, ресурсов и доступности выбранных сервисов. Победитель по качеству ответов и скорости без практических испытаний не определён.

### 1.3. Сравнение embedding-моделей

#### Назначение и объекты сравнения

Embedding-модель преобразует текст в вектор — набор чисел, используемый для поиска близких по смыслу фрагментов. При построении индекса кодируются документы, при обращении пользователя — его вопрос. Генерация окончательного ответа выполняется отдельной LLM.

Sentence-Transformers — библиотека для работы с embedding-моделями. Для сравнения выбраны две конкретные локальные модели и один облачный сервис. Исследование основано на документации; замеры на базе проекта пока отсутствуют.

| Модель | Размещение | Размерность вектора | Предел входа | Особенности применения |
|---|---|---|---|---|
| `intfloat/multilingual-e5-small` | Локально через Sentence-Transformers | 384 | 512 токенов | Многоязычная модель; для поиска используются префиксы `query: ` у вопросов и `passage: ` у документов, в том числе для русского текста |
| `BAAI/bge-m3` | Локально; в сравнении рассматривается режим dense, один вектор на фрагмент | 1024 | 8192 токена | Многоязычная модель; поддерживает также другие режимы поиска, которые не включены в это сравнение |
| `text-embedding-3-small` | API OpenAI | 1536 по умолчанию; доступно сокращение через `dimensions` | 8192 токена | Облачное вычисление векторов; исходные фрагменты и вопросы передаются провайдеру |

Характеристики: [multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small/blob/main/README.md), [BGE-M3](https://huggingface.co/BAAI/bge-m3), [OpenAI Embeddings](https://developers.openai.com/api/docs/guides/embeddings).

Размерность обозначает количество чисел в одном векторе, а предел входа — допустимую длину обрабатываемого текста. Эти параметры не являются оценками качества поиска.

#### Разбиение документов и совместимость

Ограничение E5 требует проверки длины каждого фрагмента её токенизатором с учётом префикса и служебных токенов. Передача более длинного текста с автоматическим обрезанием создаёт риск: сохранённый фрагмент будет содержать сведения, которые не участвовали в формировании вектора. Рекомендации задания о 100–300 словах или 500–1000 токенах не являются эквивалентными; параметры разбиения должны соответствовать выбранной модели.

Больший допустимый вход BGE-M3 и OpenAI даёт больше свободы при разбиении, но не означает, что максимальная длина оптимальна. Чанк с несколькими несвязанными темами может затруднять точный поиск и увеличивать объём контекста для LLM. Границы разделов и смысловая целостность остаются значимыми критериями.

Для документов и вопросов необходимы одна модель, согласованные настройки и предусмотренные моделью способы подготовки текста. Совпадение размерности у разных моделей не делает их векторы совместимыми. Смена модели или размерности требует пересоздания векторов и индекса. Вместе с индексом необходима фиксация идентификатора и версии модели, размерности, нормализации и параметров разбиения.

#### Качество поиска и скорость индексации

| Критерий | Локальные модели | Облачная модель |
|---|---|---|
| Качество поиска | Зависит от языка, терминологии, разбиения и подготовки входа; компактная E5 и BGE-M3 являются кандидатами для проверки | Зависит от тех же свойств корпуса; доступность API и размерность не доказывают превосходство |
| Вычисление векторов документов | Зависит от оборудования, длины фрагментов, размера пакета и режима вычислений; ресурсы выделяются владельцем системы | Зависит от сети, квот, пакетирования запросов и обработки на стороне провайдера |
| Обработка вопроса | После загрузки модели не требует внешнего вызова; возможна конкуренция с LLM за память и вычисления | Каждый новый вопрос требует обращения к API, если его вектор не закеширован |
| Эксплуатация | Загрузка весов, управление зависимостями и ресурсами, воспроизводимость среды | Управление ключами, лимитами, повторными запросами и доступностью сервиса |

Это архитектурная оценка факторов, а не результаты измерений. Для локального варианта CPU является отправной точкой проверки; необходимость ускорителя определяется допустимым временем обработки и замерами. Меньшая размерность уменьшает объём векторов, но сама по себе не доказывает более быструю работу модели.

Полное время построения индекса включает чтение и разбиение документов, вычисление embeddings, добавление векторов в хранилище и сохранение. В практической проверке время вычисления embeddings и полное время построения имеют разный смысл; первоначальная загрузка весов также учитывается отдельно от повторного запуска.

Для оценки поиска необходим набор вопросов с заранее определёнными релевантными фрагментами. Подходящие показатели: Recall@5 — доля релевантных фрагментов, найденных среди первых пяти результатов, и MRR@5 — средняя обратная позиция первого релевантного результата в этой пятёрке, с нулём при его отсутствии. Проверка также должна включать вымышленные термины и вопросы без ответа в базе. Само наличие ближайшего вектора не подтверждает наличие ответа; порог сходства требует настройки для конкретной модели.

Для сравнения моделей условия поиска должны быть сопоставимыми: одинаковые документы, вопросы и правила оценки, согласованные размеры фрагментов, помещающиеся в пределы всех кандидатов. Отдельный эксперимент с более длинными чанками оценивает уже конфигурацию целиком. Числовые результаты этих проверок пока не получены.

#### Стоимость владения и использования

При локальном запуске нет оплаты внешнему API за токены. Полная стоимость включает вычислительные ресурсы, хранение весов и индекса, электроэнергию и сопровождение. Уже имеющийся компьютер снижает дополнительные расходы прототипа, но не делает эксплуатацию бесплатной.

Для `text-embedding-3-small` стандартная цена составляет **0,02 USD за 1 млн входных токенов**, без применения пакетных скидок. [Тариф модели](https://developers.openai.com/api/docs/models/text-embedding-3-small).

Условный пример, не прогноз нагрузки компании:

| Операция | Обрабатываемый объём | Стоимость API |
|---|---|---|
| Первичная индексация | 1 000 000 токенов | 0,020 USD однократно |
| Индексация новых и изменённых фрагментов за месяц | 100 000 токенов | 0,002 USD в месяц |
| Векторизация 10 000 вопросов за месяц, по 50 токенов | 500 000 токенов | 0,010 USD в месяц |

Первый месяц такого сценария: **0,032 USD**, последующие при тех же объёмах изменений и вопросов: **0,012 USD в месяц**. Формула: число обработанных входных токенов / 1 000 000 × 0,02 USD. Объёмы заданы после разбиения: повторяющиеся части перекрывающихся чанков также обрабатываются и оплачиваются. Повторная отправка текстов увеличивает стоимость.

В расчёт не включены LLM, хранилище, приложение, сеть, сопровождение и возможные налоги. Доступность API и допустимость внешней обработки данных остаются самостоятельными ограничениями, рассмотренными в разделе 1.2.

#### Влияние размерности на хранение

Для несжатых векторов `float32` объём массива равен `N × d × 4` байт, где `N` — количество фрагментов, `d` — размерность. При условных 100 000 фрагментов:

| Размерность | Объём массива векторов, МБ (1 МБ = 1 000 000 байт) |
|---|---|
| 384 | 153,6 |
| 1024 | 409,6 |
| 1536 | 614,4 |

Это расчёт только массива векторов, а не размера всего индекса или необходимой RAM сервера. Тексты, метаданные, структуры поиска, модель и рабочие буферы требуют дополнительных ресурсов. Количество 100 000 выбрано для иллюстрации и не выведено из числа документов компании.

#### Промежуточный вывод

Для локального прототипа E5-small представляет вариант с небольшим объёмом векторов и строгим ограничением длины чанка. BGE-M3 представляет альтернативу для экспериментов с более длинными фрагментами; допустимые задержки и потребление памяти требуют проверки на доступном оборудовании. OpenAI упрощает эксплуатацию embedding-модели при допустимости внешней передачи текстов и наличии доступа к API.

Окончательный выбор зависит от языка и структуры будущей базы, качества поиска и ресурсов. Локальные embeddings позволяют индексировать документы и обрабатывать вопросы в собственном контуре, но использование облачной LLM на следующем этапе всё равно передаёт ей выбранные фрагменты. Без практической проверки победитель по качеству и скорости не определён.

### 1.4. Сравнение FAISS и ChromaDB

#### Объекты и границы сравнения

FAISS — библиотека поиска по векторам. ChromaDB (Chroma) — система хранения и поиска, предоставляющая коллекции записей с идентификаторами, векторами, документами и метаданными. Поэтому сравнение учитывает как поиск ближайших векторов, так и функции, которые потребуется реализовать в приложении. [Описание FAISS](https://github.com/facebookresearch/faiss), [API коллекций Chroma](https://docs.trychroma.com/reference/python/collection).

Рассмотрены FAISS на CPU с точным индексом `IndexFlatIP` и локальная Chroma Single Node. У FAISS существуют и приближённые индексы; возможности библиотеки не ограничены выбранным базовым вариантом. Распределённая Chroma и Chroma Cloud имеют другую архитектуру и не включены в данное сравнение. [Индексы FAISS](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes), [конфигурация Chroma](https://docs.trychroma.com/docs/collections/configure).

#### Функциональность и удобство работы

| Критерий | FAISS | Chroma Single Node |
|---|---|---|
| Работа с векторами | Добавление и поиск через Python API библиотеки | Добавление и поиск через API коллекций |
| Тексты и метаданные | Связь результата поиска с текстом, источником и позицией фрагмента организуется приложением или интеграционной библиотекой | Документы и метаданные доступны в записях коллекции |
| Сохранение | Индекс сохраняется в файл; тексты, метаданные и соответствие идентификаторов сохраняются дополнительно | `PersistentClient` сохраняет данные в локальном каталоге |
| Фильтрация | Фильтры по полям корпоративных документов требуют отдельной логики; поддержка отбора ID зависит от типа индекса и API | Предусмотрены `where` для метаданных и `where_document` для содержимого |
| Изменение записей | Способ обновления зависит от индекса; для небольшой базы возможна пересборка с сохранением согласованности текстов и векторов | Предусмотрены `update`, `upsert` и `delete`; `upsert` создаёт или обновляет запись по ID |
| Встраивание в приложение | Работает в процессе бота, отдельный сервис не требуется | Возможны локальный клиент и подключение к серверу через `HttpClient` |

Основания: [сохранение FAISS](https://github.com/facebookresearch/faiss/wiki/Index-IO,-cloning-and-hyper-parameter-tuning), [клиенты Chroma](https://docs.trychroma.com/reference/python/client), [операции коллекций Chroma](https://docs.trychroma.com/reference/python/collection). Ответственность приложения за согласованность данных и сложность сопровождения являются архитектурной оценкой.

Оба варианта допускают передачу заранее вычисленных embeddings. Для сопоставления хранилищ необходимы одинаковые векторы, полученные выбранной моделью. Автоматическое вычисление embeddings в Chroma требует явной настройки той же модели; иначе сравниваются одновременно и хранилище, и разные модели поиска.

#### Скорость поиска и индексации

`IndexFlatIP` выполняет точный поиск скалярного произведения перебором векторов. Он не требует обучения индекса; при росте количества фрагментов увеличивается объём работы на запрос. Для базового массива векторов используется около `4 × d` байт на запись, где `d` — размерность, без учёта текстов и служебных структур. [Индексы FAISS](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes).

В Chroma Single Node используется HNSW — граф для приближённого поиска ближайших соседей. Он позволяет искать без полного перебора, но требует построения дополнительной структуры и может пропустить часть истинных ближайших соседей. Параметры построения и поиска задают компромисс между затратами ресурсов, задержкой и полнотой результатов. Это свойство алгоритма, а не доказательство преимущества Chroma на корпусе проекта. [Настройки индекса Chroma](https://docs.trychroma.com/docs/collections/configure).

Для небольшой базы точный поиск является понятной исходной конфигурацией. Само наличие HNSW не гарантирует меньшую полную задержку: на неё влияют размер базы, фильтрация, получение метаданных и режим подключения. При росте базы FAISS также позволяет перейти к приближённому индексу, поэтому ограничение перебора относится к `IndexFlatIP`, а не ко всей библиотеке.

При проверке производительности значимы следующие отдельные показатели:

- Время добавления уже вычисленных векторов и сохранения индекса.
- Задержка поиска при заданном количестве результатов, включая получение текстов и метаданных.
- Потребление памяти, размер сохранённых данных и время загрузки после перезапуска.
- Полнота приближённого поиска относительно точного поиска на тех же векторах; она отличается от смысловой релевантности, оцениваемой по вопросам и источникам.

Генерация embeddings учитывается отдельно, чтобы не приписывать её время хранилищу. Условия сравнения должны фиксировать оборудование, количество и размерность векторов, метрику, фильтры, число результатов и одновременных запросов. Измерений проекта пока нет; количественное ранжирование по скорости не выполнено.

#### Метрика и интерпретация результатов

При использовании `IndexFlatIP` косинусное сходство получается после нормализации и документов, и вопросов до единичной длины: большее значение означает большую близость. Chroma в режиме `cosine` возвращает расстояние `1 − cosine_similarity`: меньшая величина означает большую близость. Перенос одного числового порога между этими вариантами без преобразования изменит поведение отказа при нехватке данных. [Метрики FAISS](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances), [метрики Chroma](https://docs.trychroma.com/docs/collections/configure).

Точность поиска ближайшего вектора не равна достоверности ответа. Даже точный индекс может вернуть нерелевантный фрагмент, если в базе нет нужных сведений или embedding-модель не отразила смысл вопроса.

#### Развёртывание, сопровождение и стоимость

FAISS распространяется по лицензии MIT, Chroma — Apache 2.0. При самостоятельном размещении рассматриваемых открытых версий нет тарифа сервиса за каждый поиск. Инфраструктура и сопровождение остаются статьями расходов. [Репозиторий FAISS](https://github.com/facebookresearch/faiss), [репозиторий Chroma](https://github.com/chroma-core/chroma).

| Статья затрат | FAISS в процессе бота | Chroma |
|---|---|---|
| Вычисления и память | Поиск, загрузка индекса, получение текстов; копии индекса в нескольких процессах могут увеличить расход RAM | Поиск и работа хранилища; граф индекса и служебные структуры требуют дополнительных ресурсов |
| Диск и резервные копии | Индекс, тексты, метаданные и параметры должны сохраняться как согласованный набор | Необходимы сохранение каталога данных и проверка восстановления согласованной копии |
| Разработка | Дополнительная логика соответствия ID, текстов и метаданных, обновлений и фильтрации | Готовые операции коллекций сокращают часть этой логики |
| Эксплуатация | Для одного процесса мало компонентов; общий доступ нескольких экземпляров бота требует отдельного решения | Локальный режим прост для разработки; серверный режим добавляет отдельный сервис, его наблюдение и обслуживание |

Документация Chroma предназначает `PersistentClient` для локальной разработки и тестирования, а для производственной эксплуатации рекомендует серверное размещение. Наличие серверного режима само по себе не подтверждает отказоустойчивость или достаточную производительность под нагрузкой компании. [Документация клиентов](https://docs.trychroma.com/reference/python/client).

Для Docker вариант с FAISS может состоять из одного контейнера бота с библиотекой внутри и подключённым каталогом данных. Отдельный контейнер «сервера FAISS» не требуется. Для серверной Chroma возможны отдельные сервисы бота и хранилища. Это варианты будущего развёртывания; Docker-конфигурация пока не реализована.

Полная стоимость включает ресурсы приложения и хранилища, резервное копирование, наблюдение и трудозатраты сопровождения. Числовая оценка требует конфигурации сервера, тарифа размещения и профиля нагрузки; отсутствие лицензионной платы не означает нулевой стоимости владения.

Для корпоративного решения фильтры метаданных могут участвовать в ограничении поиска, но не заменяют аутентификацию, получение актуальных прав из источников и контроль доступа на серверной стороне. Это требование относится к обоим вариантам.

#### Промежуточный вывод

FAISS с точным индексом является обоснованным кандидатом для небольшого прототипа с редкими обновлениями: понятный алгоритм, работа внутри бота и воспроизводимая пересборка. Цена простоты поискового компонента — необходимость отдельно хранить тексты и метаданные и поддерживать их соответствие векторам.

Chroma является обоснованным кандидатом при приоритете операций над документами, фильтрации и обновления отдельных записей. Её преимущество в этом сценарии связано с готовым API хранения; преимущество по скорости без замеров не установлено.

Выбор для реализации будет зафиксирован в составе общей конфигурации в разделе 1.5 с учётом embedding-модели, размещения LLM и ресурсов. Объём корпоративной базы сам по себе не определяет выбор: существенны количество чанков, частота обновлений и нагрузка.
