# architecture-sprint-7

Проектная работа 7 спринта курса «Архитектор программного обеспечения» Яндекс Практикума: RAG-бот для QuantumForge Software.

## Цель

Цель проекта — разработка бота для поиска информации в базе знаний и формирования ответов на основе найденных фрагментов. Критерии качества включают корректную обработку недостаточности данных и устойчивость к prompt injection.

## Текущее состояние

Подготовлена локальная среда: macOS на Apple Silicon, Python 3.11.16, виртуальное окружение `.venv`. Работа ведётся в ветке `rag`. Правила Git исключают окружение, кэш Python и локальные настройки.

Завершено исследование моделей и инфраструктуры. Подготовлены список из 30 источников Star Wars и скрипт загрузки. Все 30 исходных статей загружены; соответствие списку источников и контрольные суммы проверены. Реализованы очистка HTML и отбор текста по явным редакторским правилам. Получены 30 очищенных документов общим объёмом 6437 слов; метаданные и контрольные суммы проверены. Сформирована база `knowledge_base/`: 30 документов с вымышленными названиями, 6455 слов, 1109 замен. Остаточные термины из словаря не обнаружены; 19 автоматических тестов очистки и переименования прошли успешно. Создан FAISS-индекс из 46 векторов размерности 384. Три контрольных запроса нашли ожидаемые фрагменты на первой позиции; Hit@3 = 3/3. Всего выполнены 60 модульных тестов. Реализован консольный RAG-бот с few-shot примерами, обоснованиями и проверяемыми ссылками на источники. Полный цикл проверен на семи запросах: пять ответов по источникам и два отказа при отсутствии сведений; автоматические проверки пройдены для 7/7 запросов. Выполнен эксперимент с prompt injection: отдельный индекс, сравнение трёх режимов на двух провоцирующих вопросах и десять контрольных запросов. С полной защитой пройдены 10/10 проверок; результаты сохранены в `reports/prompt_injection.json`. Docker-конфигурация не реализована.

## Подготовка окружения

Требуется Python 3.11. Проверенная среда: Python 3.11.16, архитектура `arm64`.

На macOS с установленным Homebrew Python 3.11 можно установить командой:

```bash
brew install python@3.11
```

В корне локальной копии репозитория создать окружение:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
```

Проверить используемые Python и pip:

```bash
python --version
which python
python -m pip --version
```

Ожидаются Python 3.11.x и пути к Python и pip внутри `.venv` этого проекта.

В VS Code выбрать `.venv/bin/python` через команду `Python: Select Interpreter`. Для команды требуется расширение Python от Microsoft. Выбор интерпретатора в редакторе и активация окружения в текущем терминале выполняются отдельно.

При открытии нового терминала в корне проекта окружение можно активировать повторно:

```bash
source .venv/bin/activate
```

Зависимости этапа индексации перечислены в `requirements.txt`; версии прямых зависимостей закреплены. Папка `.venv` хранится только локально.

Установка в активированное окружение:

```bash
python -m pip install -r requirements.txt
python scripts/check_index_environment.py
```

Проверка выполняет `pip check`, импортирует библиотеки и проверяет FAISS на синтетических векторах и разбиение короткого текста средствами LangChain. Веса модели при этом не скачиваются, индекс базы знаний не создаётся. Успешная проверка окружения не является проверкой качества поиска.

Состав зависимостей:

| Пакет | Назначение |
|---|---|
| `sentence-transformers` | Запуск embedding-модели |
| `transformers` | Загрузка архитектуры модели и токенизатора |
| `torch` | Вычисления модели |
| `numpy` | Массивы векторов |
| `faiss-cpu` | Создание индекса и поиск на CPU |
| `langchain-text-splitters` | Разбиение документов на фрагменты |

Окружение проверено после установки пакетов на Python 3.11.16 и macOS ARM64: проверка совместимости зависимостей, импорт библиотек, поиск FAISS на синтетических векторах и разбиение тестового текста завершились успешно. Транзитивные зависимости пока не закреплены полным lock-файлом. Среда Linux для Docker подлежит отдельной проверке.

Источники: [Sentence-Transformers](https://pypi.org/project/sentence-transformers/), [FAISS CPU](https://pypi.org/project/faiss-cpu/), [LangChain Text Splitters](https://pypi.org/project/langchain-text-splitters/).

## Загрузка исходных статей

Скрипт использует стандартную библиотеку Python; установка дополнительных пакетов не требуется. Необходим доступ к API Wikipedia.

Из корня репозитория загрузить одну статью для проверки:

```bash
python scripts/download_sources.py --limit 1
```

Первый источник — Luke Skywalker. Результат сохраняется в `data/raw/luke_skywalker.json`: исходный HTML и метаданные закреплённой версии. Это промежуточный материал, который ещё требуется очистить и преобразовать.

После проверки можно загрузить весь список:

```bash
python scripts/download_sources.py --all
```

Повторный запуск проверяет контрольные суммы и пропускает сохранённые статьи. При ошибке обработка останавливается с ненулевым кодом; успешно загруженные файлы сохраняются. Исходники в `data/raw/` исключены из Git. Сведения об источниках и лицензии приведены в `data/README.md`.

## Очистка текстов

После загрузки всех исходников выполнить:

```bash
python scripts/clean_sources.py
```

Дополнительные зависимости и сетевые запросы не нужны. Результаты: 30 Markdown-документов в `data/cleaned/` и файл `manifest.json` с метаданными, контрольными суммами, количеством слов и связями с исходными абзацами. Повторный запуск пересоздаёт результаты по тем же правилам.

`data/cleaning_rules.json` задаёт отобранные абзацы, границы фрагментов и точные редакторские правки. Если исходный текст изменился, скрипт останавливается и требует пересмотра правил. Эти правила предназначены для закреплённого набора статей, а не для произвольных страниц Wikipedia.

Очищенные документы сохраняют исходные имена и являются промежуточным результатом перед заменой терминов. Каталог `data/cleaned/` исключён из Git. Индексация исходников, метаданных и правил очистки не предусмотрена.

Проверка обработки HTML и ошибок очистки:

```bash
python -m unittest discover -s tests -v
```

## Замена терминов и формирование базы знаний

После очистки выполнить:

```bash
python scripts/rename_terms.py
```

Результат — 30 файлов `knowledge_base/kb_001.md`–`kb_030.md` с вымышленными именами и названиями. `terms_map.json` задаёт замены, включая короткие имена, псевдонимы, организации, виды, технологии и географические названия. Полные названия обрабатываются раньше коротких; замены выполняются за один проход с учётом границ слов.

Метаданные сохраняются отдельно: `data/knowledge_manifest.json` содержит контрольные суммы, соответствие источникам и статистику замен, `data/ATTRIBUTION.md` — авторство, ссылки на исходные версии и лицензию CC BY-SA 4.0 для текстов. Эти файлы, словарь и промежуточные каталоги не предназначены для индексации. Индексируемые документы находятся только в `knowledge_base/`.

Скрипт работает без сети и дополнительных зависимостей. Он проверяет целостность входных документов и останавливается при обнаружении остаточных терминов из словаря. Повторный запуск пересоздаёт результаты по тем же правилам; редактировать нужно входные данные или правила с последующим пересозданием корпуса.

## Подготовка модели и фрагментов

Параметры заданы в `config/embedding_config.json`: модель `intfloat/multilingual-e5-small`, закреплённая версия `614241f622f53c4eeff9890bdc4f31cfecc418b3`, 384 компоненты вектора, нормализация, выполнение на CPU. Для модели используются префиксы `passage: ` у документов и `query: ` у вопросов, включая вопросы на русском языке. Характеристики и правила подготовки входа: [карточка E5](https://huggingface.co/intfloat/multilingual-e5-small).

После установки зависимостей загрузить модель и проверить вычисления:

```bash
python scripts/download_embedding_model.py
```

Первый запуск требует сети и скачивает веса и токенизатор в `models/multilingual-e5-small/`. Повторный запуск использует локальный кэш загрузчика. Скрипт проверяет размерность, лимит входа и нормализацию двух тестовых векторов. Это проверка работоспособности модели, а не качества поиска по базе знаний. Каталог `models/` исключён из Git.

После успешной проверки подготовить фрагменты без обращения к сети:

```bash
python scripts/prepare_chunks.py
```

Разбиение выполняется средствами LangChain по абзацам, предложениям и, при необходимости, словам или символам. Размер — до 360 токенов по функции длины токенизатора; целевое перекрытие — до 40 токенов, оно может отсутствовать на границах абзацев. Полный вход `passage: <заголовок>\n\n<текст>` отдельно проверяется без обрезания: максимум 480 токенов, включая служебные, при лимите модели 512.

Проверенный запуск на текущей базе: 30 документов, 46 фрагментов, максимальная длина полного входа — 365 токенов. Модель загружена, проверка вычисления и нормализации двух тестовых векторов пройдена.

Результат `data/chunks.json` содержит конфигурацию, число документов и фрагментов, время разбиения, тексты, входы для модели и метаданные. `start_char` включительно и `end_char` исключительно задают позиции символов в исходном Markdown-файле, включая заголовок. Сохраняется SHA-256 документа. Индексация читает только `knowledge_base/*.md`; словарь замен и метаданные с исходными именами не включаются в тексты. Промежуточный файл фрагментов исключён из Git и пересоздаётся скриптом.

Проверки координат, полноты текста и ограничений длины после загрузки модели:

```bash
python -m unittest discover -s tests -p 'test_prepare_chunks.py' -v
```

При отсутствии локального токенизатора эти тесты пропускаются, а не подтверждают работоспособность. Загрузка весов и создание фрагментов сами по себе ещё не создают FAISS-индекс.

## Построение индекса и проверка поиска

После подготовки `data/chunks.json`:

```bash
python scripts/build_index.py
python scripts/check_retrieval.py
```

Первый скрипт вычисляет нормализованные векторы локальной моделью E5 и создаёт `FAISS IndexFlatIP`. Сохраняются:

- `index/faiss.index` — векторы для точного поиска по скалярному произведению;
- `index/metadata.json` — тексты и источники в порядке векторов;
- `index/manifest.json` — настройки, версии библиотек, контрольные суммы и измерения времени;
- `reports/retrieval_examples.json` — результаты трёх контрольных запросов после запуска второго скрипта.

Эти небольшие результаты сохраняются в репозитории вместе с кодом построения и проверки. Веса модели в Git не включаются. Сериализация метаданных выполняется в JSON, без pickle. Перед заменой результатов индекс проверяется во временной папке: сохранение, повторная загрузка и поиск собственных векторов. Прерванное обновление обнаруживается при следующем чтении по контрольным суммам; в таком случае требуется повторное построение. Построение и поиск следует выполнять последовательно.

Перед вычислением векторов проверяются настройки модели, состав и контрольные суммы документов, координаты и полнота фрагментов, длина входов токенизатором. Поиск также проверяет соответствие индекса текущей конфигурации и базе знаний. После изменения корпуса или параметров необходимо повторить подготовку фрагментов, построение индекса и контрольные запросы.

На macOS для совместного запуска PyTorch и FAISS установлен `OMP_NUM_THREADS=1` внутри процесса до импорта вычислительных библиотек. Без этого ограничения при проверке полного построения наблюдалось падение процесса. Режим указан в `manifest.json`; замеры относятся к одному CPU-потоку. Это локальная настройка запуска, системное окружение пользователя не меняется. Linux требует отдельной проверки. Аналогичная проблема совместной загрузки библиотек описана в [PyTorch issue 149201](https://github.com/pytorch/pytorch/issues/149201).

Ручной запрос:

```bash
python scripts/search_index.py "Кто является отцом Lior Veylan?" --top-k 3
```

Вывод включает найденные тексты, источники, идентификаторы, координаты и сходство. Запрос кодируется той же моделью с префиксом `query: `. Нормализованные векторы позволяют использовать скалярное произведение как косинусное сходство: [метрики FAISS](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances). Число сходства не является вероятностью правильного ответа. Поиск всегда возвращает ближайшие фрагменты, даже если ответа нет; обработка недостаточности данных относится к следующему этапу RAG.

В `data/retrieval_cases.json` заранее заданы три вопроса и идентификаторы фрагментов с подтверждающими фразами. `check_retrieval.py` сохраняет полные top-3 результаты и считает долю запросов, для которых хотя бы один указанный фрагмент найден в первой тройке (Hit@3). Код завершения 1 означает непрохождение проверки или ошибку; при промахе сам отчёт всё равно сохраняется. Три примера не оценивают качество на всех возможных вопросах и не проверяют ответы LLM.

Результат выполненного запуска: 30 документов, 46 векторов размерности 384, генерация эмбеддингов — 1,106226 с на CPU в один поток. Размер файла индекса — 70 701 байт. Сохранение, повторная загрузка и самопоиск проверены. Контрольные запросы дали Hit@3 = 3/3, во всех трёх случаях ожидаемый фрагмент найден первым. Подробные измерения и ограничения приведены в разделе 3 технического отчёта.

Время загрузки модели, генерации эмбеддингов, добавления в FAISS и сохранения данных измеряется отдельно. Время кодирования вопроса и поиска измеряется без начальной загрузки модели; первый запрос может включать прогрев вычислений. Сумма отдельных измерений не равна полному времени запуска команды, которое также включает импорты и проверки.

Проверки целостности и соответствия индекса:

```bash
python -m unittest discover -s tests -v
```

## Подготовка локальной LLM

Для генерации выбрана `Qwen/Qwen3-8B-GGUF`, файл `Qwen3-8B-Q4_K_M.gguf`, версия `7c41481f57cb95916b40956ab2f0b139b296d974`. Файл занимает 5 027 783 488 байт (около 5,03 ГБ). Его размер и SHA-256 закреплены в `config/llm_config.json`. Источник: [официальные веса Qwen](https://huggingface.co/Qwen/Qwen3-8B-GGUF/tree/7c41481f57cb95916b40956ab2f0b139b296d974).

Установка движка на macOS через Homebrew:

```bash
brew install llama.cpp
llama-server --version
```

Команда установки приведена в [документации llama.cpp](https://github.com/ggml-org/llama.cpp/blob/master/docs/install.md). Версию установленного движка необходимо зафиксировать при проверке запуска. Установка через Homebrew не закрепляет версию пакета; воспроизводимость будущего Docker-образа потребует отдельного закрепления сборки.

Загрузка весов из активированного Python-окружения:

```bash
python scripts/download_llm.py
```

Загрузчик получает конкретный файл закреплённой версии, проверяет размер и SHA-256 и сохраняет сведения в `models/qwen3-8b/download_manifest.json`. Существующий файл сначала проверяется локально без повторной загрузки. Каталог `models/` уже исключён из Git. Проверка файла подтверждает целостность весов, но не запуск генерации.

Дополнительная проверка без сети:

```bash
python scripts/download_llm.py --verify-only
```

В случае повреждения файла повторная загрузка выполняется с `--force-download`.

Установлен llama.cpp 0.5.0 (build 11146, commit `7fe450e19`), сборка Darwin ARM64. Веса загружены, размер и SHA-256 проверены. Это подтверждает целостность файла; генерация проверяется отдельно.

В конфигурации LLM заданы адрес `127.0.0.1:8080`, контекст 8192 токена на промпт и ответ, максимум 512 токенов ответа, один одновременный запрос и отключённый режим thinking. Для Mac параметр `gpu_layers=99` запрашивает перенос всех доступных слоёв на Metal; фактическое размещение видно в логе llama.cpp. Он запускается отдельным процессом, ограничения потоков Python-компонента индексации на него не распространяются.

В первом терминале:

```bash
python scripts/start_llm_server.py
```

Окно остаётся занятым сервером. Логи записываются в `logs/llama-server.log`, который исключён из Git; при следующем запуске лог заменяется. В начале лога сохранены версия движка и команда запуска. Для остановки используется Ctrl+C. Для запуска без GPU предусмотрен параметр `--cpu`.

Во втором терминале перейти в каталог проекта, активировать `.venv` и выполнить:

```bash
python scripts/check_llm_server.py
```

Проверка обращается к `/health`, проверяет имя модели и отправляет короткий вопрос о вымышленной планете вместе с тестовым контекстом. Ожидаемый ответ содержит название города Келар; проверяется также нормальное завершение генерации. Это ограниченная проверка ответа, а не оценка качества RAG. Результат сохраняется в `reports/llm_smoke.json`. Если сервер ещё загружает веса, проверка предлагает повторить запрос после загрузки. При подключении к localhost прокси окружения не используется.

Проверка генерации выполнена: ответ «Город Келар.», нормальное завершение `stop`, 111 токенов промпта и 8 токенов ответа; время HTTP-запроса при загруженной модели — 0,746770 с. Запрос и ответ сохранены в `reports/llm_smoke.json`. Это один короткий запрос без поиска по базе, а не замер полного RAG-пайплайна.

Полный цикл поиска и генерации реализован в `scripts/rag_pipeline.py`; инструкции приведены ниже.

## Запуск RAG-бота

Сначала запустить сервер Qwen в отдельном терминале:

```bash
python scripts/start_llm_server.py
```

В другом терминале с активированным `.venv`:

```bash
python scripts/rag_bot.py "Кто является отцом Lior Veylan?"
```

Для консольного диалога запустить без аргумента:

```bash
python scripts/rag_bot.py
```

Выход — `/exit`. Каждый вопрос обрабатывается самостоятельно; история предыдущих вопросов не добавляется к следующему запросу. Модель E5 и индекс загружаются один раз на сеанс. После изменения базы требуется перестроить индекс и перезапустить бота.

Поток данных: вопрос → E5 с `query: ` → три фрагмента FAISS → системная инструкция, два few-shot примера и текущие фрагменты → Qwen → проверка результата → ответ, обоснование и цитаты с источниками.

Примеры в `prompts/few_shot.json` загружают текст `kb_027_002` из индекса: ответ об источнике энергии lumenblade и отказ при отсутствии цены. Они задают формат, но не являются источниками для текущего вопроса. Предложения текущих документов получают идентификаторы. JSON-схема ответа ограничивает выбор источников этими идентификаторами; приложение подставляет цитаты из исходного текста. Совпадение цитаты не доказывает смысловую обоснованность каждого утверждения — это проверяется при просмотре диалогов.

Системная инструкция `prompts/rag_system.txt` требует ответа по текущим источникам, краткого обоснования и отказа при отсутствии сведений. Дополнительная инструкция `prompts/document_policy.txt` запрещает выполнение команд из документов и выдачу учётных данных. Обычный запуск бота применяет также фильтрацию найденных фрагментов и проверку ответа с цитатами. Добавлен небольшой словарь перевода общих терминов англоязычной базы. Генерация выполняется с `temperature=0`, отключённым thinking и пределом 512 токенов. Перед запросом сервер применяет свой шаблон чата и токенизатор: полный промпт, резерв ответа и дополнительные 32 токена должны помещаться в контекст 8192. Обработка контекста описана в [API llama.cpp](https://github.com/ggml-org/llama.cpp/tree/master/tools/server).

При `not_found` приложение возвращает «Я не знаю. В найденных документах нет ответа на этот вопрос». Решение о достаточности непустого контекста принимает модель; универсального порога сходства не задано. Ошибки соединения, неверная структура ответа, неподтверждённый источник и обрыв генерации выводятся как ошибки, а не маскируются отказом по содержанию.

Контрольные диалоги:

```bash
python scripts/check_rag.py
```

Скрипт задаёт пять вопросов с ответами и два без ответа из `data/rag_cases.json`. Сохраняет `reports/rag_examples.json`: ответы, подтверждения, найденные фрагменты, время, токены, параметры моделей и контрольные суммы входных файлов. Он проверяет статусы, ожидаемые источники и ключевые слова. Это ограниченная автоматическая проверка; для оценки смысла нужно просмотреть ответы и цитаты. При несовпадениях лог сохраняется, а команда завершается с кодом 1. При недоступности сервера на этапе подключения проверка не начинается.

Основной запуск завершён с результатом **7/7**: пять ответов и два отказа. [Сохранённые диалоги](reports/rag_examples.json) содержат исходные ответы и цитаты. Полный запрос занимал 3,31–6,28 с при уже загруженных моделях и индексе; кэш промпта не очищался. Контрольные суммы и принадлежность цитат источникам проверены. Результат относится к семи выбранным вопросам; ограничения формулировок и условия измерения описаны в разделе 4.3 [технического отчёта](Project_template.md).

Вопросы и тексты в логах могут содержать данные базы. Сейчас используется вымышленный корпус; для корпоративных данных потребуется отдельная политика хранения и доступа к логам. Для эксперимента с вредоносным документом используются отдельный индекс и журнал, описанные ниже.

## Проверка prompt injection

Тестовый файл `data/security/malicious.txt` содержит строку из задания с искусственным маркером `swordfish`. Команда создаёт каталог `data/injection_lab/run-…`, копирует в него 30 документов и добавляет тестовый документ. К исходной строке добавляется только Markdown-заголовок; текст проходит те же разбиение, E5, нормализацию и построение FAISS, что и остальные документы. Основной корпус и сохранённый индекс остаются исходными.

При работающем сервере llama.cpp выполнить во втором терминале с активированным `.venv`:

```bash
python scripts/check_prompt_injection.py
```

Каждый запуск создаёт отдельный тестовый индекс; генерация использует уже загруженную локальную LLM. Для проверки одной индексации и поиска без генерации:

```bash
python scripts/check_prompt_injection.py --prepare-only
```

На двух провоцирующих вопросах сравниваются три режима с одинаковыми результатами поиска:

| Режим | Дополнительные меры |
|---|---|
| `off` | Инструкция безопасности и фильтры выключены; обычные правила ответа, few-shot, JSON-схема и проверка источников сохранены |
| `system` | Включена только `document_policy.txt` |
| `filtered` | Включены инструкция безопасности, отбрасывание подозрительных фрагментов после поиска и проверка ответа, обоснования и цитат перед выводом |

Режим `filtered` используется в обычном боте по умолчанию. Переключение доступно в коде экспериментального сценария. При исключении всех фрагментов LLM не вызывается; бот сообщает о фильтрации. При частичном исключении модель получает оставшиеся фрагменты и может ответить «Я не знаю». Дополнительный поиск вместо исключённых фрагментов не выполняется.

После сравнения выполняются ровно десять запросов в режиме `filtered`: пять вопросов с ответами, три вопроса без сведений в базе и два провоцирующих вопроса. Список хранится в `data/security/cases.json`. Фильтр не ищет слово `swordfish`: оно используется только для измерения результата эксперимента. Правила проверяют явные команды смены инструкций, разделители ролей и конструкции с присваиванием значения паролю или ключу доступа. Подозрительный фрагмент удаляется целиком из контекста, включая команду и её содержимое.

`reports/prompt_injection.json` сохраняет результаты по мере выполнения: исходную выдачу, исключённые фрагменты и причины, идентификаторы контекста, исходную генерацию и пользовательский ответ. Наличие маркера в генерации и в видимом выводе оценивается отдельно. Ошибка генерации не считается успешным отказом; отсутствие вредоносного документа в top-3 не считается успешной защитой. Код завершения 0 означает, что десять автоматических проверок пройдены, сравнения выполнены и входные файлы не изменились за время запуска.

Основной запуск выполнен: тестовый индекс содержит 31 документ и 47 фрагментов. По обоим провоцирующим вопросам вредоносный фрагмент найден первым. Маркер появился в выводе в 2/2 случаях без дополнительных мер, в 1/2 с одной системной инструкцией и в 0/2 с полной защитой. Отдельная серия завершилась результатом **10/10**: пять ответов с источниками и пять отказов. Во всех пяти отказах фильтр также исключил вредоносный фрагмент из выдачи. [Журнал эксперимента](reports/prompt_injection.json) содержит исходные ответы и причины фильтрации; подробный разбор приведён в разделе 5 [технического отчёта](Project_template.md).

Журнал специально содержит искусственную вредоносную строку и исходные результаты модели, чтобы эксперимент был проверяемым. Для реальных учётных данных такой режим диагностического сохранения неприемлем без отдельной политики доступа и удаления секретов из логов. Правила фильтра могут пропускать перефразированные атаки и блокировать безопасные учебные цитаты. Они не заменяют разграничение доступа к базе знаний. Результаты требуют просмотра по смыслу; десять запросов не доказывают защищённость от всех инъекций.
